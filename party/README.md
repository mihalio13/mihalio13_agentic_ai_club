# Тусовка

Сервіс подій з обмеженою кількістю місць, щось на кшталт спрощеного Meetup. Користувачі створюють події, інші записуються на них, коментують і бачать, скільки лишилося вільних місць.

**Стек:** Python 3.13 · Django 5.2 LTS · PostgreSQL (прод) / SQLite (локально) · WhiteNoise · Gunicorn.
JavaScript-фреймворків немає: серверний рендеринг, сувора CSP і невеликий `app.js` для зручностей.

**Інтерфейс:** власна дизайн-система без сторонніх бібліотек: світла й темна тема, адаптив під телефон, SVG-іконки, обкладинки-заглушки з градієнтами, прев'ю обкладинки перед завантаженням, доступність (клавіатура, `aria`, `prefers-reduced-motion`). Усе працює без inline-стилів і скриптів, тож CSP лишається суворою.

## Можливості

| # | Вимога | Як реалізовано |
|---|--------|----------------|
| 1 | Акаунти | Реєстрація та вхід за email і паролем (Argon2), вихід через POST, зміна пароля, «Забули пароль?» з листом |
| 2 | Створення події | Назва, опис, дата й час, кількість місць, обкладинка (JPEG/PNG/WebP ≤ 5 МБ), публічна чи приватна |
| 3 | Головна | Майбутні публічні події за датою, пошук за назвою (кирилиця без урахування регістру), пагінація |
| 4 | Сторінка події | «Іду» / «Скасувати», лічильник і прогрес-бар місць, коментарі |
| 5 | Керування автора | Редагування, видалення (з підтвердженням), список учасників, видалення учасника без права повторного запису (можна дозволити знову) |
| 6 | Приватні події | Відкриваються лише за посиланням-запрошенням; посилання можна перегенерувати, тоді старе перестає працювати |
| 7 | Мій профіль | «Я йду» та «Мої події», включно з минулими |

## Швидкий старт (локально)

Потрібен лише [uv](https://docs.astral.sh/uv/): він сам поставить Python 3.13 і залежності.

```bash
# 1. Встановити uv (якщо ще немає)
curl -LsSf https://astral.sh/uv/install.sh | sh

# 2. Залежності + конфіг
uv sync
cp .env.example .env            # за замовчуванням DJANGO_DEBUG=1 і SQLite

# 3. База даних
uv run --env-file .env python manage.py migrate

# 4. (необов'язково) адміністратор для /admin/
uv run --env-file .env python manage.py createsuperuser

# 5. (необов'язково) демо-події, щоб було на що подивитись
uv run --env-file .env python manage.py seed_demo

# 6. Запуск
uv run --env-file .env python manage.py runserver
```

`seed_demo` працює лише при `DJANGO_DEBUG=1`. Демо-користувачі мають непридатний пароль, тож увійти під ними неможливо.

Відкрийте <http://127.0.0.1:8000>.

### Змінні середовища

| Змінна | Обов'язкова | Опис |
|--------|-------------|------|
| `DJANGO_DEBUG` | ні (дефолт `0`) | `1` лише для розробки. Без неї застосунок стартує в безпечному прод-режимі |
| `DJANGO_SECRET_KEY` | **так, у проді** | Довгий випадковий рядок. Без нього при `DEBUG=0` застосунок не запуститься |
| `DJANGO_ALLOWED_HOSTS` | так, у проді | Домени через кому. На Render підставляється автоматично |
| `DJANGO_CSRF_TRUSTED_ORIGINS` | для свого домену | Напр. `https://tusovka.example.com` |
| `DATABASE_URL` | ні | PostgreSQL URL. Без неї використовується `db.sqlite3` |
| `TRUSTED_PROXY_COUNT` | за проксі | Кількість reverse-proxy перед застосунком (Render: `1`), щоб правильно визначати IP для rate limit |
| `DJANGO_ADMIN_URL` | ні | Шлях до адмінки (дефолт `admin/`) |
| `EMAIL_HOST`, `EMAIL_PORT`, `EMAIL_HOST_USER`, `EMAIL_HOST_PASSWORD`, `DEFAULT_FROM_EMAIL` | для листів у проді | SMTP для листів «Забули пароль?». Без `EMAIL_HOST` листи пишуться в лог сервера (зручно локально) |

## Тести та перевірки

Усі тести запускаються однією командою:

```bash
uv run pytest
```

210 тестів, покриття ≈ 97 %. Більшість перевіряють не щасливий шлях, а спроби зламати застосунок:

- **IDOR / права:** чужий користувач не може редагувати, видаляти, керувати учасниками, перегенерувати запрошення чи видаляти чужі коментарі (отримує 404).
- **Приватні події:** недоступні без запрошення через *кожен* ендпоінт (сторінка, обкладинка, запис, коментарі). Перегенероване посилання відкликає доступ.
- **Гонки:** 20 потоків одночасно записуються на подію з 5 місцями, і місць ніколи не стає більше.
- **Шкідливі файли:** SVG з JS, HTML під виглядом PNG, decompression bomb, обрізаний файл, EXIF з GPS (вирізається).
- **XSS, CSRF, open redirect**, підробка `X-Forwarded-For`, підміна `author`/`is_staff` у формі.
- **Brute force:** rate limit на вхід (за IP і за акаунтом), реєстрацію, коментарі, запис, запрошення.
- **Property-based (Hypothesis):** пошук не падає на будь-якому Unicode-рядку, rate limiter пропускає рівно `limit` запитів.

Інші перевірки (вони ж запускаються в CI і pre-commit):

```bash
uv run ruff check . && uv run ruff format --check .   # лінтер і форматування
uv run mypy .                                         # strict-типізація
uv run bandit -q -c pyproject.toml -r .               # статичний аналіз безпеки
uv run pip-audit                                      # вразливості в залежностях
uv run pre-commit install                             # усе це перед кожним комітом
```

CI ([`.github/workflows/tusovka-ci.yml`](../.github/workflows/tusovka-ci.yml) у корені репозиторію) запускає тести на SQLite **і** на PostgreSQL, а також `manage.py check --deploy`.

## Деплой (Render, безкоштовно)

1. Запушити репозиторій на GitHub.
2. На [render.com](https://render.com): **New → Blueprint**, обрати репозиторій. [`render.yaml`](../render.yaml) у корені репозиторію (з `rootDir: party`) створить PostgreSQL і веб-сервіс, а `DJANGO_SECRET_KEY` згенерує автоматично.
3. `build.sh` встановлює залежності **з перевіркою хешів**, збирає статику, застосовує міграції і запускає `check --deploy`.

На будь-якому іншому Linux-хостингу: задати змінні середовища, виконати `./build.sh`, запустити
`gunicorn config.wsgi:application`.

## Рішення щодо безпеки та надійності

- **Доступ до подій вирішується в одному місці** (`events/access.py`). Без прав відповідь 404, а не 403, тож не можна навіть дізнатися, що приватна подія існує.
- **Запрошення:** токен на 256 біт. Після переходу за посиланням він зберігається в сесії, а користувача перенаправляє на чисту адресу. `Referrer-Policy: same-origin` не дає токену витекти на сторонні сайти.
- **Бронювання місць атомарне:** `SELECT … FOR UPDATE` на PostgreSQL, `BEGIN IMMEDIATE` на SQLite. Плюс `UNIQUE(event, user)` і `CHECK` на кількість місць у самій БД. Не можна зменшити кількість місць нижче вже записаних, записатися на минулу подію чи двічі.
- **Обкладинки** перекодовуються у WebP (формат перевіряється за вмістом, EXIF видаляється, є ліміт пікселів) і зберігаються в БД. Так вони не губляться на хостингах з ефемерним диском, а для приватних подій віддаються лише тим, хто має доступ.
- **Заголовки:** сувора CSP без `unsafe-inline`, `X-Frame-Options: DENY`, HSTS, `nosniff`, Permissions-Policy, `no-store` для HTML.
- **Сесії:** HttpOnly, Secure, SameSite=Lax; ID сесії змінюється при вході; вихід лише через POST з CSRF.
- **Паролі:** Argon2, мінімум 10 символів, перевірка на популярні паролі й на схожість з email, максимум 128 символів (захист від DoS на хешуванні).
- **Приватність:** email інших користувачів ніде не показується, лише ім'я.
- **Rate limit** у кеші в БД: спільний для всіх воркерів gunicorn.
- **Стабільність:** ліміт розміру запиту (413), власні сторінки помилок, `/healthz` з перевіркою БД, `conn_health_checks`, залежності з хешами.

## Структура

```
accounts/   користувач (email замість username), реєстрація, вхід, зміна пароля
events/     моделі, форми, в'юхи; access.py — права, services.py — атомарні операції,
            images.py — безпечна обробка картинок
core/       middleware (CSP, ліміт запиту), rate limiter, сторінки помилок, healthz
config/     налаштування (settings.py — прод за замовчуванням, settings_test.py — тести)
templates/  HTML-шаблони;  static/ — CSS, JS, favicon
tests/      pytest + Hypothesis
```
